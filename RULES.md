## Rules discovered during this build
**Data and architecture**
- TanStack Query owns all Supabase data; Zustand owns UI state only. Never mix.
- All colours via `--accent` and other CSS custom properties; no hardcoded hex in components.
- `today` is never computed at module load; use state refreshed on `visibilitychange` and at midnight.
- Set logs: `weight` and `reps` are nullable (null when `is_skipped`).
- Meso week numbers are calendar weeks, Monday-anchored: `differenceInCalendarWeeks(date, mesoStartDate, { weekStartsOn: 1 }) + 1`, or `startOfWeek(date, { weekStartsOn: 1 })` for a window boundary. Never `differenceInWeeks`. Pass `weekStartsOn` explicitly. A fixture whose answer turns on a week's end derives that verdict from its dates the same way, prints it, and pins the Sunday / Monday boundary (chunk 44).
- **Stage-exclusion:** a `v2_set_logs` row with `parent_set_id` (or `v2_week_plan_sets` with `parent_week_plan_set_id`) is a drop stage and is never an independent set — excluded from set counts, numbering, avg reps/RIR, top set, e1RM eligibility, planned-set lists. **Volume is the one exception (stages count).** Enforce via `setGroupLogic.ts` (`headsOnly`, `groupSetLogs`, `groupWeekPlanSets`, `canAddStageTo`, `isStageOfSkippedHead`) or the 009/011 views, never ad hoc. A stage of a skipped head contributes nothing. Orphan dropsets (`is_dropset` with null parent) render as independent heads.
- Dropset write paths pass the parent id directly from the tap (ADD STAGE); no inference anywhere except the 007 backfill and copy-week reconstruction (`copySetsWithGrouping`, which re-maps ids by group).
- Deleting a dropset head deletes stages first (descending), head last; ADD STAGE is disabled while a head is mid-delete; awaited deletes need `networkMode: 'always'` so offline rejects instead of hanging.
- e1RM: RIR-adjusted Epley (`reps + rir`); sets with null RIR are skipped, never defaulted to 0; a session with no RIR anywhere is excluded, not mixed in unadjusted; headline is a percentage, never an absolute weight.
- Weights are stored in kg. An edit whose displayed value is unchanged returns the original stored kg (`resolveEditedWeightKg`); a program exercise's unit is written as a resolved literal at creation.
- **Compare a logged weight with a planned one as the exercise's unit shows them** (chunk 43): the shown 19.8 lbs, typed, stores 8.98 kg against the seed's planned 9 kg, so a raw comparison reads a set done as planned as changed on every lbs exercise; compare `toDisplayWeight` of both.
- **REVIEW reads a head log's `stage_kind` as the type as done** (chunk 43; TASKS 43: "the log's kind vs the planned kind"): head-log writers keep it the planned set's kind unless the type changed in the workout, and null on a switch to Normal (TASKS 62). A read without the column reads as null (`SetLog.stageKind` is optional) and turns every planned staged set with no drop logged into "You made set N a normal set" (reproduced in chunk 43's second review): 56 reads logs as `fetchSession` does (`v2_set_logs(*)`, `toSetLog`). A dropset whose head has no kind logs null too, so its log can't show a switch to Normal (DECISIONS 141).
- **REVIEW sees a type change on a set that wasn't done only through the set's `retyped` row** (chunk 43's fourth attempt, DECISIONS 150 (b); break-proven in its review): a skipped log's own kind or warmup flag, and a `pending_stages` row (a count, keyed by a log), are never read for it. So every writer that skips or abandons a planned set leaves the session's `retyped` row for it as it is: SKIP THIS SET (61), "Skip the rest of this exercise" and a swap's skipping of the original's remaining sets (59), unlog (63, which keeps or writes the row) and finishing with the set unlogged (64). Only a delete turns it into `deleted` (Adam's change-row rule; 61, 62). A swap also keeps logging the replacement's sets with no planned set, as today (59): REVIEW reads a log of another exercise on a planned set as no comparison at all, so a set retyped before the swap and logged as the replacement under its planned set would lose its type item (probed in the review; the seed's week-1 swap has that shape, with no change rows).
- `EARLIER THIS WEEK` is the shipped label for the reference panel's secondary slot; SPEC/TASKS still say `THIS WEEK` (it collided with `PlanTargetsPanel`). Not a bug.
- Plan's SETS / STRUCTURE choice is page-local, not persisted (chunk 29).
- **Coach and `api/**` rules** (permanent-record tables, `api/**` module imports and `.js` extensions, endpoint order, model pins, advisory only, `COACH_USER_ID` pairing, the analysed meso's id, what Coach may read, the position-match convention, Coach's imports of `referenceLogic`/`setGroupLogic`): still true, moved word for word to HISTORY.md, "2026-10-11 docs prune". Read them before any Coach or `api/**` change.
- New tables use the standard `for all using/with check (user_id = auth.uid())` RLS; deviations (select+insert only; read-only libraries) are deliberate and documented in the migration.
- A bare `select` from a table shared across accounts through any RLS-bypassing path must carry an explicit `user_id = <Adam>` filter — including one-off investigation queries.
- **One read path for program exercises (chunk 9):** `src/features/programs/runProgramExercises.ts` is the only reader of a run's `v2_program_exercises`. The program-tab list excludes `week_only` and `removed_at` rows; a week's list comes through `v2_week_plan_exercises`. `node scripts/check-program-exercise-reads.mjs` enforces it at every boundary, and each exception is listed in the script with its reason.
- **Carry fields are unread (chunk 27):** `carry_program_exercise_id` / `carry_position` stay in `v2_week_plan_exercises` (dropping them would be destructive) but nothing reads them: copying (client and `v2_plan_week` 038), apply-ahead and deload matching use each row's own id and position. Swap, reorder and the apply-ahead repoint still clear them. Don't add a reader.
- **A removed read can be a guard (chunk 27):** the carry lookup a swap/reorder did first was also what made it fail on a row the week no longer had; removing it turned a stale-screen error into a silent orphan write. When a chunk removes a read in front of a write, keep (and test) whatever failure it gave.
- **A deload marked with rules on keeps the session's pre-deload sets in `v2_week_plans.deload_restore`, and UNMARK writes them back whole** (`applyDeloadRestore`: every set deleted, the copy re-inserted by `program_exercise_id`). A write that changes such a session's exercises leaves the copy stale: unmarking then brings back sets of exercises the session no longer lists and empties ones it gained (chunk 45's review, executed; DECISIONS 142).
- **Since chunk 45 a CHANGE THE PROGRAM save rewrites a not-started deload session's saved copy with the same landing rules** (DECISIONS 142): one update of `v2_week_plans.deload_restore`, the only column of that table 043 may write. Every other writer that changes a session's exercises still leaves the copy stale (the rule above).
- **A CHANGE THE PROGRAM swap inserts a new program-exercise row and soft-removes the old one; only `v2_program_exercises.replaces_program_exercise_id` (043, chunk 47) records what replaced what** (chunk 45). A done session's planned sets name their exercise only through the program-exercise row, so the row can't change in place. `v2_session_exercise_swaps` is the live-session swap, the `carry_*` columns are 1.1's unread links, and a position match can't tell a swap from a removal plus an add in the same place.
- **A week-dependent run changed in 1.1 has its exercise list in its weeks, not in its run copy** (chunk 45's review, executed). 1.1's week view made a `week_only` row for SWAP or ADD and dropped the week's rows for REMOVE; the program tab went in 1.1 and Make default is stable-only. So the run copy's list can be stale against the weeks. A rule that reads the run copy's list for such a run (143's copy, CHANGE THE PROGRAM's draft) undoes those changes, and a `week_only` row is outside every 1.2 action (DECISIONS 149).
- **A migration that drops a column ships after the code that stops using it** (chunk 12, 2026-10-06). Code that no longer references the column works with or without it. So the order inverts: code first, every device takes the update banner, then the drop. Check every bundle still in use for writes to the column, not only the bundle TASKS names (chunk 11's own bundle wrote `target_reps`).
- **Break proofs restore from a `cp` backup, never `git checkout --`** on a file with uncommitted changes. Checkout reverts every uncommitted edit, not just the break; chunk 9's builder silently lost its fix that way and caught it by md5. A break is one exact replacement that must match once: one that never fired reads as caught (chunk 39). After a loop of breaks, what is on disk (a build, screenshots) is the last break's: rebuild from the restored code before reading it (chunk 40).
- **Flagged migrations the reviewer may merge (Adam, 2026-10-05, phase 1; DECISIONS D29):** one that changes no existing row (only adds tables, columns, indexes or rows; replaces a function or view; or relaxes a constraint), once `migration-replay`, `check-embeds-local.sh` and the reviewer's scratch-copy check (existing rows' counts and fingerprints unchanged) all pass. Still Adam's: 12, 24, 25. Migration first, code after a green deploy. Adam extended it to TASKS-1.1's 038–040 (P1, P4; 2026-10-10).
- **Workout screen unchanged for plain sessions (Adam, 2026-10-05; DECISIONS D30):** superseded for the workout screen in 1.2 by behaviour parity (R4, Adam 2026-10-13; TASKS-1.2 Process notes): from chunk 58a, a plain session logs the same row, times the same rests and finishes the same way, proven by tests of the written payload and the rest target. Its wording: HISTORY.md, "2026-10-15 chunk 43 review 2".
- **One workout on several weekdays exists** (G14, Adam's second account, 2026-10-05): one shared plan row per week covers every weekday that workout is on, so planning or marking deload on it affects all of them. Keep that behaviour until the program is edited; never convert such a program automatically. The planner (chunk 11) prompts for per-weekday workouts or keep-as-is; chunk 25 adds the sequence choice (DECISIONS 44 (a)); deload marking (chunk 21) says the shared row covers several days. Any chunk that assumes one weekday per workout (scheduler, move-a-session in chunk 24) must handle this case in its fixtures.
- Check UI at 375 px, not just desktop.
- Anything that starts a run (or ends the active one) runs in one transaction under a per-user advisory lock; the app's two-request complete-then-insert can leave two active runs.
- A new table the app reads or writes is added to `TABLES` in `scripts/verify-rls.mjs` in the same change; a table not listed there is not RLS-checked, and `verify-rls-tables.test.mjs` fails until it is. Only a deliberately world-readable catalog goes in `PUBLIC_BY_DESIGN`, with the migration that makes it so cited.
- **A table created before any app code uses it goes in `TABLES_AHEAD_OF_THE_APP`** in `scripts/verify-rls.mjs` (chunk 36; TASKS-1.2 says "added to `TABLES`", which `verify-rls-tables.test.mjs` refuses for a name no `.from()` uses): probed exactly like `TABLES`, so its policy and grants are checked from the day it exists. The chunk whose code first calls `.from()` on it moves the name into `TABLES` (`verify-rls-tables.test.mjs` fails until it does) and deletes it from the ahead list (`verify-rls-ahead.test.mjs` fails until it does). Today: `v2_run_schedules`, `v2_week_review_decisions`, `v2_session_set_changes` (first reads planned in chunks 50, 56 and 61).
- **A `pending_stages` row's `stage_count` is the set's total number of drops, logged ones included** (chunk 46): 042's check `(stage_kind is not null) = (stage_count > 0)` can't hold a count of drops still to log once it reaches 0, so the count never shrinks as drops are logged. Chunks 62 and 63 write the total, never a kind with a count of 0.
- **A column that is no longer read is left out of a named column list, and a named list fails the whole read when one of its columns is missing** (chunk 48): `select('*')` still returns a column the mapper ignores, so `v2_programs` is read by `PROGRAM_COLUMNS` without `deload_rules`; PostgREST answers `400` / `42703` to a list naming a column the database lacks, where `*` simply returned less. A column a migration adds joins such a list only once that migration is live where the code runs, and the list is probed against the real PostgREST (with a made-up-column control) before it ships.
- **A queued write is "never sent" only when no send of it has started and none has failed** (chunk 57): `sendStarted` goes into IndexedDB, awaited, before an upsert's first request, and a retry keeps a write it resets marked; `attempts` alone is reset by the retry and can't see a reply lost on a locked phone. Only such an upsert cancels with a later delete of its row, and only inside the single-flight pass, never when the delete is queued: a pass already running holds the upsert in its snapshot and would send it after its delete had gone (a ghost row; break E04, which passed both earlier versions of the order tests and fails the merged ones).
- **A queued delete's payload is `{ id }`, and the whole request is `delete().eq('id', id)`; its session and, for a stage log, its head go beside it on the queue item** (`sessionId`, `parentSetId`; chunk 57): the finish's wait (`hasQueuedWritesFor`), the "couldn't sync" notice and a head's delete read them there. A producer (61, 63) calls `queueSetLogDelete` once per log, stages first and the head last. Every queue item goes out through `.from(item.table)`, the one spelling `verify-rls-tables.test.mjs` allows in that file: a path that names its table another way fails it (executed in chunk 57's second review).

**Database / migrations**
- **Production runs pg-safeupdate:** DELETE/UPDATE without WHERE fails via the API, inside functions too; use `where true` (041).
- The `supabase/postgres` image isn't always pullable from this container (rate limits, mirror limits, proxy policy): an apt PostgreSQL with the roles/auth bootstrap in TASKS-1.2.md's appendix replays every migration for SQL-level checks, as a stand-in only — Postgres 17 and pg-safeupdate stay unproven until CI's `migration-replay`.
- Before merging a migration that changes or removes existing data (merging deploys it), Adam runs and records a row count on **every table the file mentions** (target, FK, join), scoped to Adam's `user_id` where one exists, and re-counts after. An add-only migration is proven by `migration-replay` plus the reviewer's scratch-copy count/fingerprint check instead (Repo facts → Migration flow).
- Migrations are deployed by Supabase from master (Repo facts); nothing is applied, transported or pasted by hand. The hand-apply rules (transport, Monaco `getValue`/`setValue`, the "Potential issue detected" dialog, applied-text hash checks) are in HISTORY.md (2026-10-04, migration switch); Checks that lied #3 and #4 stay as history of the SQL Editor.
- Prove constraints by attempting to violate them (`23514`, `23503`, `23505`, zero rows written); prove `on delete set null`/cascade by really deleting a throwaway parent; prove read-only/append-only RLS through the anon-key client.
- Write fixtures as sequential statements (a `DO` block with local variables), never sibling data-modifying CTEs (single snapshot — a sibling's write is invisible to an `UPDATE`). Same rule is load-bearing in `021` step 2a, where a subquery must see pre-merge state.
- Throwaway data: label it (`TEST-…`, `ZZ_TEST_…`, "throwaway"), scope to Adam, delete in FK-safe order, and prove cleanup with `count(*)` against the baseline — not by the UI looking empty. Deleting a meso leaves its sessions behind (an orphaned `in_progress` one keeps being picked up as "the" session) — delete those too.
- Apply additive migrations before deploying code that writes the new columns (e.g. `measure_set_time` before `settingsService` sends it).
- Live schema probe that reads no data: `GET /rest/v1/<table>?select=<columns>&user_id=eq.<Adam>&limit=0` with the anon key answers `200 []` when every column exists and `400 / 42703` when one doesn't — always include a made-up-column control.

- **An insert through `jsonb_populate_record` (043's planned executor) gets NULL, not the column's default, for every column its row leaves out** (chunk 45, executed on the replay image): an op's insert row names every NOT NULL column, `created_at` included on `v2_program_sets`, `v2_program_superset_blocks`, `v2_run_schedules` and `v2_week_plan_exercises`. TASKS-1.2's "`probe-live-columns.mjs <NNN>`" means that.

- **A logged warmup may hold no weight and no reps; a working set's log may not** (035's `v2_set_logs_check`: `is_skipped or is_warmup or (weight is not null and reps is not null)`; chunk 46's second review, executed on the replay). **Verification and process**
- Live browser verification against real data is a hard gate whenever a task calls for it (see Escalation 1). Live tests write only with an explicit go-ahead.
- Commands for Adam are for Windows. His `>` redirect has produced UTF-16 files (PowerShell's), so anything that reads his output must accept UTF-16 (`compare-schema.mjs` does). The pinned CLI is `npx --yes supabase@2.119.0`; `db query --linked` goes through the Management API (login only, no DB password); never `db dump --dry-run` (prints the password).
- Dry-run technique (no credential handling): from the dev-server tab, dynamic `import()` the real compiled modules and call them with the app's own already-authenticated `supabase` singleton. Throwaway scripts (`*.ts` at repo root) are deleted immediately, never committed, and `git status` is checked afterwards.
- Plain `vite` dev does not serve `api/**`: exercise endpoints on a deployed build or by invoking the handler directly with a minimal request/response. Do not grep for a deferred live check and call it verified — carry it forward by name.
- Adversarial review: independent reviewers per dimension, each finding independently re-verified against current source; report raw vs confirmed counts, fix confirmed bugs, keep refuted findings noted. Say which findings got adversarial verification and which were checked by hand.

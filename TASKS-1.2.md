## Process notes

- **Where everything runs.** Builders and the reviewer work in this cloud environment (CONTEXT.md, "This cloud environment"): Docker with the real `supabase/postgres` image for scratch replays (`bash scripts/replay-migrations.sh --keep`; the apt stand-in in the appendix only when the pull fails, and then Postgres 17 and pg-safeupdate stay unproven until CI); Playwright + Chromium for screenshots and for the staging app; the staging database through `STAGING_SUPABASE_URL` / `STAGING_SUPABASE_ANON_KEY` as the staging accounts. Production is reachable only for the anon-key column probe at the release; nothing in the build reads or writes it.
- **Branches and merges.** Each chunk is one PR from its builder branch into `staging`, squash-merged by the reviewer once review passes; never stacked (retro, section 3.7). A chunk with a migration and code is one PR; the migration is proven live on staging (the Supabase deploy on the merge, the grants check, R2's call) before the next chunk that reads it starts. Every chunk leaves staging usable: the app on `overload-v2-staging.vercel.app` signs in, opens every tab and logs a set after every merge (the reviewer's smoke, below).
- **Migrations on staging.** `migration-replay` (with `check-embeds-local.sh` inside it) is the required check on every PR. `check-migration` runs on every schema chunk; a flag no longer stops a chunk: the reviewer merges into staging and logs the migration, one line, under "For the release" in DECISIONS.md (Escalation 8 as patched for 1.2). After each schema merge the reviewer: (1) reads every `Supabase Preview` run on the merge commit and treats anything but success as a failed deploy, which is blocking (Escalation 15); (2) asks each **new table** `GET /rest/v1/<table>?select=id&limit=0` with the anon key, signed out, and expects `200` — `42501` means the branch didn't run the migration as `postgres` and the grants are missing (`verify-rls` counts `42501` as a pass, so it can't catch this); (3) runs `node scripts/probe-live-columns.mjs <NNN>` against staging for the new columns. **R2:** `v2_apply_ops` (043) and `v2_plan_week` (045) are each called once on staging as the signed-in test account in the chunk that creates them (47, 53), before any screen depends on them; creating them in the replay is not proof (pg-safeupdate only checks a function's body when it runs).
- **No migration in 1.2 changes an existing row** (042 adds columns with defaults or null and empty tables; 043 creates a function and adds one nullable column, `v2_program_exercises.replaces_program_exercise_id` (DECISIONS 143, 2026-10-15); 044 adds one nullable column, `v2_set_logs.added_place`, with no default (chunk 46m); 045 replaces a function; 047 (59's) adds one nullable column to `v2_session_exercise_swaps`).
```sql
with slots as (
  select distinct on (wp.mesocycle_id, wp.workout_day_id, wp.sequence_position)
         wp.mesocycle_id, wp.workout_day_id, wp.sequence_position, wp.id as week_plan_id
    from v2_week_plans wp
    join v2_mesocycles m on m.id = wp.mesocycle_id and m.status = 'active' and m.user_id = '12e79b69-9891-4f53-a7cf-650edd83659f'
    join v2_programs p on p.id = m.program_id and p.kind = 'run' and p.planning_type = 'week_dependent' and p.schedule_type = 'sequence'
   where wp.user_id = '12e79b69-9891-4f53-a7cf-650edd83659f' and wp.is_deload = false
     and exists (select 1 from v2_week_plan_sets s where s.week_plan_id = wp.id)
   order by wp.mesocycle_id, wp.workout_day_id, wp.sequence_position, wp.week_number desc
), lists as (
  select sl.*, (select string_agg(x.program_exercise_id::text || '@' || x.position, ',' order by x.position, x.program_exercise_id)
                  from v2_week_plan_exercises x where x.week_plan_id = sl.week_plan_id) as list
    from slots sl
)
select l.mesocycle_id, wd.name as workout, count(*) as slots, count(distinct l.list) as different_lists
  from lists l join v2_workout_days wd on wd.id = l.workout_day_id
 group by l.mesocycle_id, wd.name
having count(distinct l.list) > 1;
```

```sql
-- bootstrap.sql: what the supabase/postgres image provides and the migrations use
create role anon nologin; create role authenticated nologin; create role service_role nologin bypassrls;
create role app_migrator login createrole createdb bypassrls;   -- stands in for Supabase's non-superuser "postgres"

create schema auth; create table auth.users (id uuid primary key, email text);
create or replace function auth.uid() returns uuid language sql stable as $$
  select nullif(coalesce(current_setting('request.jwt.claim.sub', true),
         (current_setting('request.jwt.claims', true)::jsonb ->> 'sub')), '')::uuid $$;
create or replace function auth.role() returns text language sql stable as $$
  select nullif(current_setting('request.jwt.claim.role', true), '')::text $$;

grant select on auth.users to app_migrator, authenticated, service_role;
```

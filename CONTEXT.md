## What this is
Overload is a strength training PWA for a serious intermediate-to-advanced lifter: programs, weekly planning, live session logging and history. It is three layers — Program (what exercises) → Weekly Plan (sets + RIR targets per session per exercise) → Session Log (what actually happened) — on a Supabase backend shared with Northstar v2, single user.

Phase 1 of the Overload Planner Extension (the [P1] items in SPEC.md) is built and closed out (2026-10-09). Its rules, answers included, are tagged [P1.1] in SPEC.md and planned in TASKS-1.1.md (chunks 27–35). Rest, tempo, the warmup routine and grouping stay run-wide; per-week storage is a later revision, kept in TASKS-1.1's appendix. ## Standing UI rule (Adam, 2026-10-10; every fix from now on follows it)
"Show by default only what's used on every set or every visit. On a set row: set number, weight, reps, RIR. Everything else — set kind, tags, rest override, swap, reorder, remove, delete — lives behind a ⋯ menu on the row or exercise it belongs to. A feature that's set shows a small marker on its row (e.g. a tag shows as a compact label only on sets that have one). An unset feature shows nothing: no empty fields, chips or placeholders."

23. **A preservation check on default values** (2026-10-03): an old-client upsert "left the new columns untouched" while they still held their defaults, which proves nothing. Set non-default values first.
24. **Waiting on one check-run id** (2026-10-04): the `Supabase Preview` run first seen on 027's merge commit stayed `in_progress` indefinitely while a later run on the same commit had already succeeded; a watcher keyed to the first id would have waited forever. Read all runs of a check by name on the commit, and confirm a deploy by its effect (`probe-live-columns.mjs`).
25. **Replay green, scratch checks green, every new column live — and the app broke** (2026-10-04): 027's second `v2_mesocycles → v2_programs` FK made `fetchMesos`'s embed ambiguous (`PGRST201`), so production showed no mesocycles. SQL-level checks can't see PostgREST relationship resolution; `check-embeds-local.sh` can (DECISIONS 38).
26. **A live check scoped to Adam's user_id, read as "no such data exists"** (2026-10-05): L6 found no program with one workout on two weekdays, so G14 was declared void — but Adam has a second account, which has exactly that. Every Adam-scoped live result describes his main account only; say so when using it to rule a case out, and don't call a spec gap void on it.
27. **A green required check on a PR that still read `blocked`** (2026-10-05): after #23 was retargeted to master, `migration-replay` was started by `workflow_dispatch` on its head and passed, but GitHub kept the PR `blocked`. The dispatched run didn't count as the PR's check. And the stacked branch turned out to lack two master merges (#20, #21), so the dispatched run had tested a tree master would never get. A PR's checks count only when the PR's own `pull_request` run passes on the merged tree.
28. **"Compared by hand"** (2026-10-06): chunk 9's builder reported TS and SQL copies "structurally identical" after reading both. An executed comparison on 6 scenarios was needed before it counted. The double-swap carry bug was in exactly the part a reading glosses over (the existing carry). Parity claims need an executed comparison.
29. **"Deliberate scope decisions" that remove existing behaviour** (2026-10-06): chunk 13's builder flagged as judgement calls that a superset member loses prefill, swap, skip and ADD SET. D30 can't catch it (its fixture has no superset), and every test passed. A new grouping/layout feature must keep every per-item action the item already has. Read a builder's "scope decisions" as possible regressions, not as answers.
30. **A D30-safety rule proven only in a pure module** (2026-10-07): chunk 16 kept legacy null-kind dropsets on the global timer, with a resolver unit test, but the hook that maps `stage_kind` into the resolver was untested — promoting null to dropset there passed all 1110 tests. A compatibility rule needs a real-session test at the layer that applies it, not just at the pure function.
31. **An unbounded history query under PostgREST's row cap** (2026-10-08): chunk 23's cross-run reference query read every set log for the screen's exercises with no order and no paging; `max_rows = 1000` (supabase/config.toml) would silently return an arbitrary 1000 once history grew, dropping last week's session. Every history read either pages (ordered, `.range()` until a short page) or is bounded.

32. **A passing test that asserted the bug** (2026-10-10, B2): `MoveSessionSheet.test.tsx` had "offers all 7 days of the session's own week", written to the chunk's wording, so a sheet offering past days passed green for a whole chunk. When a rule is "only X", test what must be *absent*, on a day where something is already past (today's own weekday decides what's past).
33. **An empty read standing in for "no rows"** (2026-10-10, B1): a select filtered to Adam's user_id with the anon key returns `[]` whether the rows exist or not, because RLS hides them. If unreachable and empty give the same signal, the read proves nothing; only a signed-in read (Adam's) can.

## Rules discovered during this build
**Data and architecture**
- TanStack Query owns all Supabase data; Zustand owns UI state only. Never mix.
- All colours via `--accent` and other CSS custom properties; no hardcoded hex in components.
- `today` is never computed at module load; use state refreshed on `visibilitychange` and at midnight.
- Set logs: `weight` and `reps` are nullable (null when `is_skipped`).
- Meso week numbers are calendar weeks, Monday-anchored: `differenceInCalendarWeeks(date, mesoStartDate, { weekStartsOn: 1 }) + 1`, or `startOfWeek(date, { weekStartsOn: 1 })` for a window boundary. Never `differenceInWeeks`. Pass `weekStartsOn` explicitly.
- **Stage-exclusion:** a `v2_set_logs` row with `parent_set_id` (or `v2_week_plan_sets` with `parent_week_plan_set_id`) is a drop stage and is never an independent set — excluded from set counts, numbering, avg reps/RIR, top set, e1RM eligibility, planned-set lists. **Volume is the one exception (stages count).** Enforce via `setGroupLogic.ts` (`headsOnly`, `groupSetLogs`, `groupWeekPlanSets`, `canAddStageTo`, `isStageOfSkippedHead`) or the 009/011 views, never ad hoc. A stage of a skipped head contributes nothing. Orphan dropsets (`is_dropset` with null parent) render as independent heads.
- Dropset write paths pass the parent id directly from the tap (ADD STAGE); no inference anywhere except the 007 backfill and copy-week reconstruction (`copySetsWithGrouping`, which re-maps ids by group).
- Deleting a dropset head deletes stages first (descending), head last; ADD STAGE is disabled while a head is mid-delete; awaited deletes need `networkMode: 'always'` so offline rejects instead of hanging.
- e1RM: RIR-adjusted Epley (`reps + rir`); sets with null RIR are skipped, never defaulted to 0; a session with no RIR anywhere is excluded, not mixed in unadjusted; headline is a percentage, never an absolute weight.
- Weights are stored in kg. An edit whose displayed value is unchanged returns the original stored kg (`resolveEditedWeightKg`); a program exercise's unit is written as a resolved literal at creation.
- `EARLIER THIS WEEK` is the shipped label for the reference panel's secondary slot; SPEC/TASKS still say `THIS WEEK` (it collided with `PlanTargetsPanel`). Not a bug.
- Plan-view compact mode is page-local, not persisted.
- Permanent-record tables (`v2_coach_session_analyses`, `_week_analyses`, `_meso_analyses`, `_qa_exchanges`) have no update path. Prompt or tag changes are prospective only; a row generated under an old prompt/tag stays that way and is never "fixed". Exercise identity is denormalised into analysis JSON (no FK to `exercises`).
- New tables use the standard `for all using/with check (user_id = auth.uid())` RLS; deviations (select+insert only; read-only libraries) are deliberate and documented in the migration.
- Modules reachable from `api/**` take an injected `SupabaseClient` and must not value-import `src/lib/supabase.ts` (no `import.meta.env` in Node). Every relative import in that chain needs an explicit `.js` extension. Strip BOM/zero-width/non-ASCII characters from `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` before use.
- Coach endpoint order: verify JWT → user gate → return an existing row if present (idempotency) → validate/re-derive eligibility server-side (never trust the client) → assemble → model call → check `stop_reason` before parsing or saving (`max_tokens`/`refusal` → error, nothing written) → insert persisting `response.model`, the exact `input_snapshot`, `prompt_version` and tokens → return. Catch `23505` and return the winning row. A paid-but-unsaved generation returns its content in the error body and is logged.
- Pin dated model snapshots for Haiku (`claude-haiku-4-5-20251001`); Sonnet 5 is `claude-sonnet-5` with no suffix. Haiku 4.5 rejects `effort`. Sonnet thinking tokens count toward `max_tokens`. Bump the `*_PROMPT_VERSION` whenever a prompt changes.
- Coach is advisory only: no AI write access to anything; the model never picks a Q&A category (the originating screen does); no Northstar data.
- `COACH_USER_ID` and `VITE_COACH_USER_ID` must hold the same UUID; nothing enforces it — re-check by hand after any env change. Wrong server value → 403s; wrong client value → feature unreachable.
- A bare `select` from a table shared across accounts through any RLS-bypassing path must carry an explicit `user_id = <Adam>` filter — including one-off investigation queries.
- Mesocycle Analysis must be given the analysed meso's id, never the active meso's.
- **One read path for program exercises (chunk 9):** `src/features/programs/runProgramExercises.ts` is the only reader of a run's `v2_program_exercises`. The program-tab list excludes `week_only` and `removed_at` rows; a week's list comes through `v2_week_plan_exercises`. `node scripts/check-program-exercise-reads.mjs` enforces it at every boundary, and each exception is listed in the script with its reason.
- **Carry fields are unread (chunk 27):** `carry_program_exercise_id` / `carry_position` stay in `v2_week_plan_exercises` (dropping them would be destructive) but nothing reads them: copying (client and `v2_plan_week` 038), apply-ahead and deload matching use each row's own id and position. Swap, reorder and the apply-ahead repoint still clear them. Don't add a reader.
- **A removed read can be a guard (chunk 27):** the carry lookup a swap/reorder did first was also what made it fail on a row the week no longer had; removing it turned a stale-screen error into a silent orphan write. When a chunk removes a read in front of a write, keep (and test) whatever failure it gave.
- **A migration that drops a column ships after the code that stops using it** (chunk 12, 2026-10-06). Code that no longer references the column works with or without it. So the order inverts: code first, every device takes the update banner, then the drop. Check every bundle still in use for writes to the column, not only the bundle TASKS names (chunk 11's own bundle wrote `target_reps`).
- **Known gap (found 2026-10-06, rechecked by reading `useWeekPlan.ts` 2026-10-10):** eight plan-editing mutations still use TanStack's default network mode (`useAddSet`, `useAddStage`, `useRemoveSet`, `useCopyFromPreviousWeek`, `useCopyWorkoutFromPreviousWeek`, `useSwapWeekExercise`, `useAddWeekExercise`, `useRemoveWeekExercise`), so offline they pause instead of failing, against the house rule; the other six set `networkMode: 'always'`. Not fixed: a small separate change, raised with Adam.
- **Break proofs restore from a `cp` backup, never `git checkout --`** on a file with uncommitted changes. Checkout reverts every uncommitted edit, not just the break; chunk 9's builder silently lost its fix that way and caught it by md5.
- **Flagged migrations the reviewer may merge (Adam, 2026-10-05, phase 1; DECISIONS D29):** one that changes no existing row (only adds tables, columns, indexes or rows; replaces a function or view; or relaxes a constraint), once `migration-replay`, `check-embeds-local.sh` and the reviewer's scratch-copy check (existing rows' counts and fingerprints unchanged) all pass. Still Adam's: 12, 24, 25. Migration first, code after a green deploy. Adam extended it to TASKS-1.1's 038–040 (P1, P4; 2026-10-10).
- **Workout screen unchanged for plain sessions (Adam, 2026-10-05; DECISIONS D30):** any chunk touching the workout screen or rest timer (13–16 and any other) proves before merging that a session with none of the new features renders, logs and times rests exactly as before: plain sets, an existing dropset, no supersets/warmups/tags/tempo/rest overrides. The proof is a jsdom snapshot of the full session screen taken on master before the chunk, compared with the branch, plus a test that logs a set and checks the row written. Any difference that isn't a new feature blocks the merge.
- **One workout on several weekdays exists** (G14, Adam's second account, 2026-10-05): one shared plan row per week covers every weekday that workout is on, so planning or marking deload on it affects all of them. Keep that behaviour until the program is edited; never convert such a program automatically. The planner (chunk 11) prompts for per-weekday workouts or keep-as-is; chunk 25 adds the sequence choice (DECISIONS 44 (a)); deload marking (chunk 21) says the shared row covers several days. Any chunk that assumes one weekday per workout (scheduler, move-a-session in chunk 24) must handle this case in its fixtures.
- Coach modules may read only `v2_` tables and `exercises` (id, name, tags — nothing else from it); the Q&A "advisory only / never touches user data" properties are kept true by shape (`assembleAppMechanicsContext` takes zero parameters; `QA_ROUTES` is `Object.freeze`d because it decides model and cost tier). `APP_MECHANICS_REFERENCE` is hand-written prose no test can catch drifting — update it whenever rating vocabularies, dropset behaviour, week numbering, or unit resolution change.
- Position-match convention: session A is the earlier/baseline side; `deltaPercent = (e1rmB − e1rmA) / e1rmA × 100`; the per-set eligibility gate there does *not* require `parentSetId == null` (a second stage is a legitimate comparison item), unlike the whole-session e1RM headline.
- Check UI at 375 px, not just desktop.
- Coach imports `referenceLogic.ts` (`resolveExerciseReference`, `resolveSecondaryReference`) and `setGroupLogic.ts`, and reads the plan through `program.schedule`, `v2_week_plan_sets` → `v2_program_exercises(exercise_id)` and `workout_day_id` equality. While Coach must stay unchanged, new behaviour in those areas goes in new functions; the existing exports stay byte-identical.
- Anything that starts a run (or ends the active one) runs in one transaction under a per-user advisory lock; the app's two-request complete-then-insert can leave two active runs.
- A new table the app reads or writes is added to `TABLES` in `scripts/verify-rls.mjs` in the same change; a table not listed there is not RLS-checked, and `verify-rls-tables.test.mjs` fails until it is. Only a deliberately world-readable catalog goes in `PUBLIC_BY_DESIGN`, with the migration that makes it so cited.

**Database / migrations**
- Before merging a migration that changes or removes existing data (merging deploys it), Adam runs and records a row count on **every table the file mentions** (target, FK, join), scoped to Adam's `user_id` where one exists, and re-counts after. An add-only migration is proven by `migration-replay` plus the reviewer's scratch-copy count/fingerprint check instead (Repo facts → Migration flow).
- Migrations are deployed by Supabase from master (Repo facts); nothing is applied, transported or pasted by hand. The hand-apply rules (transport, Monaco `getValue`/`setValue`, the "Potential issue detected" dialog, applied-text hash checks) are in HISTORY.md (2026-10-04, migration switch); Checks that lied #3 and #4 stay as history of the SQL Editor.
- Prove constraints by attempting to violate them (`23514`, `23503`, `23505`, zero rows written); prove `on delete set null`/cascade by really deleting a throwaway parent; prove read-only/append-only RLS through the anon-key client.
- Write fixtures as sequential statements (a `DO` block with local variables), never sibling data-modifying CTEs (single snapshot — a sibling's write is invisible to an `UPDATE`). Same rule is load-bearing in `021` step 2a, where a subquery must see pre-merge state.
- Throwaway data: label it (`TEST-…`, `ZZ_TEST_…`, "throwaway"), scope to Adam, delete in FK-safe order, and prove cleanup with `count(*)` against the baseline — not by the UI looking empty. Deleting a meso leaves its sessions behind (an orphaned `in_progress` one keeps being picked up as "the" session) — delete those too.
- Apply additive migrations before deploying code that writes the new columns (e.g. `measure_set_time` before `settingsService` sends it).
- Live schema probe that reads no data: `GET /rest/v1/<table>?select=<columns>&user_id=eq.<Adam>&limit=0` with the anon key answers `200 []` when every column exists and `400 / 42703` when one doesn't — always include a made-up-column control.

**Verification and process**
- Live browser verification against real data is a hard gate whenever a task calls for it (see Escalation 1). Live tests write only with an explicit go-ahead.
- Commands for Adam are for Windows. His `>` redirect has produced UTF-16 files (PowerShell's), so anything that reads his output must accept UTF-16 (`compare-schema.mjs` does). The pinned CLI is `npx --yes supabase@2.119.0`; `db query --linked` goes through the Management API (login only, no DB password); never `db dump --dry-run` (prints the password).
- Dry-run technique (no credential handling): from the dev-server tab, dynamic `import()` the real compiled modules and call them with the app's own already-authenticated `supabase` singleton. Throwaway scripts (`*.ts` at repo root) are deleted immediately, never committed, and `git status` is checked afterwards.
- Plain `vite` dev does not serve `api/**`: exercise endpoints on a deployed build or by invoking the handler directly with a minimal request/response. Do not grep for a deferred live check and call it verified — carry it forward by name.
- Adversarial review: independent reviewers per dimension, each finding independently re-verified against current source; report raw vs confirmed counts, fix confirmed bugs, keep refuted findings noted. Say which findings got adversarial verification and which were checked by hand.
- Read the actual current file/section before editing or citing it; check code instead of assuming ("confirmed, not assumed"). Report expected results as expectations until checked; report outcomes faithfully.
- Don't launch a background duplicate of a check that already ran inline; if one is in flight, stop it or account for it in the next message.
- Commit and push only when asked. At the end of every session, commit CONTEXT.md to the working branch — never to master. Isolate a standalone deploy from unrelated uncommitted work with `git stash push --keep-index` plus an isolated typecheck; split unrelated work into separate commits; byte-diff restored files rather than trusting a typecheck.
- A new rule discovered mid-build is written into this file's rules in the same session, not left only in a log.
- A chunk's TASKS verification can pass while the built thing contradicts SPEC's wording (chunk 3: "3 rows, stages locked" passed with label-only rows; SPEC says "each as a row with weight and reps"). Review each chunk against the SPEC text in its brief as well as its verification list, and put SPEC's exact words in the brief.
- The cloud environment's network policy denies `overload-v2-sage.vercel.app` (403 to CONNECT; Chromium `ERR_TUNNEL_CONNECTION_FAILED`, probed 2026-10-03); the Supabase host is reachable. Live-app checks can't run from this container (DECISIONS.md 31); Adam does the live checks.
- A fresh container has no `node_modules`: run `npm ci` before typecheck/test/build.
- Anything added in front of an offline-capable write (e.g. planning the week before START) must be best-effort: its mutation uses `networkMode: 'always'` and any failure falls back to what the write used before, so the write still happens offline (chunk 8: TanStack's default `'online'` paused the planning call offline and START hung).
